# RFP-022 LEZ programs (LEZ v0.4.0-rc3, `bafd07be`; rc1 before branch `lez-rc3`)

- `token/`: the wrapped-token program. It's a copy of the Logos Names `wallet-tokens` prototype (same messages, so the stock wallet moves it publicly and privately), plus:
  - `MintBy`: a definition whose authority is `Authority::Program(id)` accepts mints from that program's actors only. The bridge's code is the mint authority. The authority is typed since the 2026-11-14 security fixes: on LEZ rc3 a program id is its loader header's account id, whose key the deployer holds, and before the fix that key could sign `Mint`/`SetAuthority` as the authority id (review C1, `research/security-review-2026-11-14.md`). A program authority never mints by a signature and is never rotated; an account authority never mints by `MintBy`.
  - `BurnWithNotice`: burn, then tell another program what was burned and why (a 32-byte memo), in the same transaction.
- `bridge/`: the bridge program.
  - **Claim:** checks the deposit's Merkle path in private, asserts the vault root was attested, spends the claim nullifier, and mints the full denomination through the token program. Clients claim against the newest attested root (an older root narrows the anonymity set).
  - **One-time recipient (default for private claimers):** `Claim`/`ClaimAttested` carry `recipient_opening: Option<[u8; 32]>`. With `Some(o)` the claimer's actor mints to `A = V.blinded(o)` (LEZ's blinded alias, `SHA256(tag | V | o)`), computed inside its own private execution from its resolved account id `V`. The deposit commitment still binds `V`: another account with the same secret and opening is refused. The public effect, the token's `MintBy` and its `Credit` name `A`, never `V`; the wallet resolves `A` back to `V` inside the proof because the opening is in `V`'s witness. The CLI defaults `o = SHA256("RFP022/alias" | k)` for a private `--from`; `--reveal-recipient` opts out and mints to `V` by name (deliberate, never the default). A public claimer always mints to itself: an alias of a public account can be neither delivered nor published.
  - **Float (fee sponsoring):** a fresh private claimer holds no native LEZ for its in-proof fee, and funding it from a public account links the two. The config's own account holds a float of native LEZ that anyone tops up (`lez-bridge fund-float`, a plain native transfer to the config address). `Config::sponsor_amount` (admin: `AdminOp::SetSponsor`, CLI `set-sponsor`; 0 = off) is paid from the float to the one-time address `A` of every claim that has one, in the claim's own transaction (`native_token::custody_transfer` under the config seed); the wallet receives it inside the proof and pays the fee from it (LEZ runs the fee entry after the root's whole subtree). Each deposit draws the float at most once (the claim nullifier). `show` prints `sponsor_amount` and `float`. The float has no withdrawal path.
    - **Empty float:** the native transfer fails, so the whole claim fails: nothing minted, nullifier unspent, float untouched (tested). On the chain: if the float is short when the claim is built, the wallet's simulation fails before proving, and the CLI checks the float first and stops with a message. If it empties between proving and inclusion and the claimer held less than the fee before the transaction (the sponsored case), the proof carries no fee fallback (LEZ `privacy_preserving_circuit/src/output.rs` `fee_fallback`), settlement fails and the sequencer drops the transaction: not charged, nothing spent. If the claimer already held enough for the fee (e.g. a second claim into the same account), the proof has a fallback and the failed claim is included as a charged revert: the fee is taken from that balance, the claim nullifier stays unspent.
    - **Without sponsoring** (`sponsor_amount` 0): fund the claimer with `lez-bridge shield --from F --to V`, which credits a fresh one-time address of `V` (random opening, kept only in the proof), so `F` is publicly linked to that address only, by amount and time.
    - **Burns are not sponsored.** The burner's sender address is a per-message presentation alias picked by the wallet, not a witnessed opening, so the stock wallet would not deliver a credit sent to it inside the proof (it promotes only credits to the account or its witnessed openings, LEZ `wallet/src/lib.rs` ~1590-1604); and burns can be split (ten 100s against one claimed 1000), so per-burn sponsoring is bounded by burned denominations, not deposits. A burner pays its own fee, e.g. from what is left of the claim's sponsorship (set `sponsor_amount` to cover a claim fee plus a burn fee; a claim cost ~9.1M on the local sequencer).
  - **What a private claim still publishes:** the token, the denomination, the time, the root (stand-in) or the anchor (RFP-021) asserted (claim against the newest one), the nullifier, the one-time address `A`, and the fixed sponsor amount paid to `A`. The claimer's account id `V` and the funding account `F` appear nowhere in it (to be confirmed by the proving run: grep the blocks for `V`, `F` and, as the positive control, `A`). Wallet quirks: a fee reserve may publish a low balance (`min(headroom, balance)`), and a fee refund to the payer's alias publishes its amount.
  - **PDA admission:** every effect to a bridge PDA (config, root, nullifier) carries the seed that derives it (`with_pda_seeds`), so LEZ admits a new PDA by seed; the CLI no longer attaches unsigned admission evidence for them (it mentions them as plain public accounts). The token's `BurnWithNotice` keeps `pda_seeds` empty: its issuer is the token program, which cannot seed the bridge's config, and the config already exists when anyone burns.
  - **Burn:** the token's `BurnWithNotice` reaches the bridge config, which checks that the amount is exactly one denomination, counts it, and emits `Exited { token, denom, E }`. The bound is by value per token (total burned ≤ total claimed), so ten 100s can exit against one claimed 1000.
  - **Init is the deployer's:** `Initialize` (CLI `init`) is signed by the bridge's own header account (the deploy key; `--payer` pays), names admin, freezer and attestor (never the header), and is refused once the config exists. The old first-come `Init` is refused (review H1).
  - **cfg_id is derived, not supplied:** `init` takes the vault, EVM chain id and the LEZ chain id (the chain's Bedrock channel id, read from the chain by the CLI, `chain-id`); the zone id is the root-source id the program derives (`source-id`); the program computes `SHA256(keccak("RFP022/cfg/v1") | u256(evmChainId) | vault | lezChainId | zoneId | programId)` with its own id. The vault computes the same from `block.chainid` and `address(this)`, so it needs the bridge program id (`lez-bridge program-id`) before it is deployed; `lez-bridge cfg-id` prints the expected value.
  - Admin: registry, append-only denominations (no duplicates), freeze, two-step admin handover. Delisting (`DeregisterToken`) only means the vault takes no new deposits: earlier deposits stay claimable and burns go through. Freezing is what stops claims and burns.
  - **Freeze:** minting (claims) and redemption (burns) have separate flags, globally and per registered token: `mint_frozen` and `burn_frozen` on the config and on each token. `Freeze { eth_token, mint, burn }` sets the named flags for one token (`Some`) or globally (`None`); `Unfreeze` clears them the same way. A flag left false is untouched, and a call naming neither is refused. The freezer or the admin may freeze; only the admin unfreezes. A claim is refused if minting is frozen globally or for its token, a burn if redemption is, and the stand-in root attestation if minting is frozen globally. A frozen claim fails with the same error at either level. CLI: `lez-bridge freeze --by F [--eth-token T] --mint --burn` and `lez-bridge unfreeze --admin A [--eth-token T] --mint|--burn`; `show` prints all four flags. **No admin timelock today** on freezer changes or lifting freezes (M4 adds one). The Ethereum vault has its own, independent freeze.
  - **Refusals:** every claim failure that depends on the deposit (a witness that proves no deposit under its root, a root never recorded, a storage proof or anchor witness that does not verify, a spent nullifier) panics with one text, `claim refused` (`CLAIM_REFUSED`), and prints no value. Texts that depend only on public data stay distinct (`minting is frozen`, `token not registered`, `bad denomination`, ...). See "Refusals" in the crate docs of `bridge/src/lib.rs` and `bridge/tests/panic_texts.rs`. The CLI runs the same checks natively before sending and names the cause locally (root not attested, anchor not finalized, proof does not verify, already claimed, frozen, wrong denomination); those messages never leave the machine. The hidden `--no-precheck` flag (tests only) skips that diagnosis so a refused claim reaches the program.
  - **Roots:** the config fixes the source at creation (`Config::root_source`; no instruction changes it).
    - Stand-in (`Initialize`): an attestor records vault roots (`AttestRoot`); `Claim` asserts the root PDA.
    - RFP-021 (`InitializeAttested`, which also checks the attestation instance exists for the chain): `ClaimAttested` carries an `eth_getProof` account + storage proof that the vault's `isDepositRoot[root]` (slot `keccak256(abi.encode(root, 83))`, `VAULT_DEPOSIT_ROOT_SLOT`; re-check with `forge inspect BridgeVault storage-layout` whenever the vault's storage layout changes) is `true` under an execution anchor. The claimer's actor verifies it; publicly it only sends `AssertAnchor(instance, chain, anchor)` to the attestation program, and the config refuses the claim unless the attestation program, instance, slot index, vault and chain id the claimer used are its own. The deposit root is no longer published. The nullifier is `SHA256("RFP022/nfc" | k | dest | token | u256(denom))` since the 2026-11-14 fixes (before: `SHA256("RFP022/nfc" | k)`, which let anyone who learned `k` burn the deposit with a cheaper one of their own, review H2).
    - Each mode refuses the other's root recording and claims.
- `attest/`: RFP-021, Ethereum state attestation (see the crate docs of `attest/program/src/lib.rs` and `attest/core/src/lib.rs`).
  - `core/` (`eth_attest_core`, what a consumer links; no BLS): instance config/store/anchor accounts, messages, `AssertAnchor`, and the inclusion library: storage slot, account field and receipt-log statements with `Eq`/`Ne` predicates and deterministic ids, under a state-root anchor or a block-hash anchor plus header RLP. `testkit` feature: synthetic tries/headers/receipts for tests.
  - `program/` (`eth_attest`): the program. Helios consensus-core 0.12.0 verifies bootstraps and updates **in the submitter's own actor** (meant to run as a private, locally proved execution: an update is 37–46M cycles, above the 10M public cap); only a 520-byte `Advance { prev, next }` (two ~260-byte summaries) reaches the instance's store PDA, which accepts it only from this program's code and only if `prev` equals its state. Instances are PDAs keyed by `SHA256(tag | program | borsh(config))`; config is write-once. Finalized execution anchors (block hash; state root before Gloas) get one PDA each, kept forever. **Deploy with an immutable program header.**
  - `probe/` (`eth_attest_probe`): reference consumer (verify one statement in its own actor, then `AssertAnchor`).
  - `cycles/`: executor-only cycle counts (own workspace). `fixtures/`: Sepolia (Gloas) and mainnet (Fulu) light-client data copied from `../attest-spike`.
- `methods/`: the token and bridge guests (bridge workspace), plus `attest_guest` and `attest_probe_guest` (own workspaces with their own `[patch]` sets, built by `attest/cycles` and, for deployment, by `attest/methods`).
- `release/` + `methods/release_guest`: **G3, the release proof** `BridgeVault.release` verifies (own workspace, excluded from this one).
  - `release/core` (`release_core`, only `risc0-zkvm`'s SHA-256): private `k, ethDest, token, denom, maxRelayFee, cfgId, leaf index, 32-sibling path`; public `relayer, relayFee`. Computes `E`, the vault's exit leaf, the root and `nf = SHA256("RFP022/nfr" | k)`, refuses `relayFee > maxRelayFee`, and commits the 256 bytes `abi.encode(cfgId, root, nf, token, denom, ethDest, relayer, relayFee)` as the raw journal, so `sha256(journal)` is exactly the vault's release digest (RISC Zero's journal digest). The guest takes no root: a wrong secret/path/index/field gives a root the vault never recorded (`UnknownExitRoot`), or a digest that doesn't match the seal if a real root is substituted. Formulas are copies of `bridge_core`'s; the host tests check they agree.
  - `release/host` (`release_host`, EXECUTOR ONLY): tests, cycle counts and the cross-language fixture (`release/fixtures/`, copied to `vault/test/fixtures/`, replayed by `vault/test/ReleaseVector.t.sol`). 36.4K user cycles, 1 segment (2^16 total) per release.
  - Exit roots are recorded only at the end of each `update()`: a client must build its path against a batch-end root (newest is best: larger anonymity set).

## Position recovery from the wallet seed (`client/`, RFP-022 F9 and R5)

`client/` (`bridge_client`) is pure logic: the KDF, the deposit request, the chain-data model, the scan. The CLI (`cli/src/recover.rs`) supplies the wallet keys, an Ethereum JSON-RPC and the LEZ sequencer. The full spec is in the crate docs of `client/src/lib.rs`. In short:

- **Root per account**, from key material the wallet re-derives from the seed phrase (the LEZ wallet does not keep the seed itself): a public account's signing key, a private account's authorization secret key (`ask`, not the viewing key). `PRK = HMAC-SHA256("RFP022/bridge/root/v1", account_secret)`.
- **Secrets**: `HMAC-SHA256(PRK, "RFP022/bridge/key/v1" | cfgId | kind | accountId | index(u64 BE) | ctx | 0x01)`, where `ctx` holds every other input of the commitment (deposit: token, denom; exit: token, denom, ethDest, maxRelayFee). The output is a master secret `s`; the programs' secret is `k = SHA256("RFP022/ck" | s)` (deposits) or `k' = SHA256("RFP022/ek" | s')` (exits); a future Ethereum-side reclaim will use `SHA256("RFP022/nfrc" | s)`. Deposits made with a raw `--secret` have no `s` and will not be reclaimable that way.
- **Why every input is bound:** the nullifiers hash the secret alone, so one secret behind two commitments would strand the second position. With every input bound, an index reused by a restored client or a second device gives the same `C` (the vault refuses it before taking funds) or an unrelated secret. Index sequences are per tuple.
- **Exits:** the release address is seed-derived by default (a fresh address per exit, key exportable with `eth-key`), so recovery needs nothing. With `--eth-dest 0x..` the user must name that address again at recovery. `maxRelayFee` defaults to the vault's 2% cap; the scan also tries 0 and every value ever on the menu. A note-to-self that would make any address recoverable needs a new burn field (program change, next version).
- **Scan:** all `Deposit`, `StateUpdated`, `Released` and `RelayFeeMenuSet` logs of the vault (bounded ranges, split on refusal, retried, resumable), the deposit tree rebuilt and checked against every logged root; every LEZ block, keeping the applied transactions that name the bridge config; then per account and tuple, indexes until `--gap` (20) unused in a row. Deposits are claimable or claimed (nullifier PDA seen); exits burned, in the exit tree, or released.
- **What the scan reveals:** the Ethereum RPC sees the same vault-wide log filter for every user; the sequencer sees block downloads. `--lez-mode point` instead asks for each found deposit's nullifier account (the sequencer learns which; it skips exits). Opt-in.

CLI: `deposit-request` (prints the commitment and the `logosdep1...` request of `web/deposit`, format v1, never a secret), `claim --key-index N` / `claim-attested --key-index N` (leaves and leaf index from the vault's logs; with a raw `--secret`/`--secret-file` too when `--leaves` is left out: logs up to Ethereum's finalized block through `--eth-rpc`, the demo v2 vault's logs read from its creation block by default; `--eth-rpc` takes a comma-separated list tried in order, and a read that finds fewer deposits than the vault's `depositCount()` or another `depositRoot()` is refused, never used: `public-demo/RUNBOOK.md` (not published) §15), `burn` without `--exit` (derived `E`, refuses an `E` already burned or an off-menu fee), `recover`, `positions`, `eth-key` (all with the global `--json`). The cache (`<wallet home>/bridge-client/<cfgId>.json`, mode 600) is only a cache.

Relayed public claim (`cli/src/relay.rs`, rc3): `claim --relay` claims into a public `--from` of this wallet that holds no native LEZ (also a never-used account): it signs the claim, and the relay co-signs as the fee payer and submits. With no value it reaches the relay through the `--sequencer` endpoint (JSON-RPC `bridge_relayInfo` / `bridge_relayClaim`, served by the demo chain's filter); `--relay http://127.0.0.1:PORT/relay` talks to a loopback relay directly (tests); `--dry-run` asks the relay to check only. `relay-cosign` (hidden) is the relay's side, run by `public-demo/relayer/relayer.py`: strict decode, the claim pre-checks, a simulation, then the payer's signature. Stand-in claims only (`claim-attested --relay` is not built). See `DESIGN.md` §3.6.

**Names Wallet scheme (`--names-app APP`, global).** Under the Names Wallet the bridge mini-app never holds a key: its core module asks the wallet's `app_secret` (Names branch `bridge-sdk`, `docs/wallet/BRIDGE-SDK.md`). That is `m = HKDF-SHA256(salt "logos-names/app-secret/v1", account_secret, info "logos-names/app-secret/v1/info" | len-prefixed app, scope, context | accountId | index)` and the app gets `SHA256(tag | m)`. The bridge uses scope `RFP022/deposit` with `context = cfgId | token(20) | u256(denom)` and tag `RFP022/ck` (the value is `k`, `m` is `s`); `RFP022/exit` with `cfgId | token | u256(denom) | ethDest | u256(maxRelayFee)` and `RFP022/ek` (`k'`); `RFP022/release` with `cfgId | token | u256(denom) | u256(maxRelayFee)` and `RFP022/release-key` (the release-address key, rehashed with SHA-256 in the 2^-128 case that it is not a valid scalar). `kdf::AccountRoot::names_app` reproduces it from the account's key, so with a wallet restored from the Names Wallet's phrase, `lez-bridge --names-app lez_bridge recover` (and `deposit-request`, `--key-index` claims, derived burns, `eth-key`) find and use what the mini-app made. Only accounts of the phrase's key trees count, as in the Names Wallet. Its cache is `<cfgId>.names-<APP>.json`. Vectors: `client/tests/vectors/kdf-names-v1.json` (Python, `gen_names_vectors.py`, which also checks the Names branch's own `app_secret.rs` vectors); `client/tests/kdf_names.rs` pins both. Deposits made with the v1 KDF or a raw secret keep their own path.

**`--emit-call PATH` (claims and burns), `--secret-file PATH`, `--json`, exit codes:** see `modules/CLI-CONTRACT.md`. `--emit-call` runs the same plan and local checks as a send, then writes the Names Wallet `propose_private_call` JSON to a new 0600 file instead of sending (`cli/src/call.rs`); nothing is proven or sent.
