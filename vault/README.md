# BridgeVault (RFP-022, Ethereum side)

`src/BridgeVault.sol` locks ERC-20s and ETH in fixed denominations for the private LEZ bridge.

- **Deposits:** `deposit(token, denomIndex, C)` and `depositETH(denomIndex, C)`.
  - SafeERC20, so USDT-style tokens that return nothing work.
  - A balance-delta check refuses fee-on-transfer tokens.
  - Each leaf goes into an append-only SHA-256 tree of depth 32 (the same zero hashes as the Ethereum deposit contract).
  - Every root is kept forever (`isDepositRoot`).
- **Outbound state:** `update(journal, seal)` checks a G2 proof against a fixed image ID, then appends exits. The journal must chain on the current state (`StaleState`) and move it (`NoStateAdvance`), so an applied journal can't be replayed as long as states never repeat (a real G2 batch always moves the LEZ tip forward).
- **Release:** `release(...)` checks a G3 proof whose journal binds recipient, relayer and fee, then spends a nullifier after the release delay.
- **Solvency is enforced by the contract itself:** claims ≤ deposits, burns ≤ claims and releases ≤ burns, per token and denomination. Fees are capped at 2%, and the fee withdrawal can only take accrued fees.
- **Admin:** registry with decimal checks, append-only denominations, fees, caps, release delay (with an immutable minimum), freeze, two-step admin handover, and an admin timelock (`adminDelay`, immutable constructor parameter).
  - Caps (F#11): per-token and global deposit and release caps over a rolling window (two-bucket sliding estimate). Global caps count each token by an admin-set `capWeight` (global units per smallest token unit, scaled by 1e18; 0 exempts the token). Any cap rejection is `CapExceeded` and consumes nothing, so the same call can be retried later. `capState(token)` and `globalCapState()` return the current usage. The estimate is not a hard bound: in the worst case close to 2x a cap can pass within one window length.
  - Freeze (F#14): deposits and releases are frozen separately, per token or globally (`freeze`/`freezeAll(deposits, releases)`); the freezer or admin freezes immediately, while lifting a freeze (`Action.Unfreeze` / `Action.UnfreezeAll`) goes through the admin timelock. Only the global release freeze stops `update`.
  - Admin timelock (M4 / red-team B1.5; closed in code for new deployments, not deployed on Sepolia yet; tests: `test/AdminTimelock.t.sol`, `test/AdminTimelockRoles.t.sol`, `test/AdminTimelockRules.t.sol`): `adminDelay` is an immutable constructor parameter enforced in `[MIN_ADMIN_DELAY (1 hour), MAX_ADMIN_DELAY (30 days)]` (the Sepolia scripts' `2 days` and the local scripts' `1 hour` are placeholders, not decided values: **ask the owner before deploy**). Every admin action that weakens safety must be queued via `schedule(action, params)` (recording `eta = now + adminDelay` and emitting `ActionScheduled`) and executed via `execute(action, params)` only while `eta <= now < eta + ADMIN_GRACE_PERIOD` (`7 days`), clearing the schedule entry so it cannot execute twice. Either the admin or the freezer may veto any pending action via `cancel(id)`. An `Unfreeze`/`UnfreezeAll` scheduled before the latest `freeze`/`freezeAll` (`lastFreezeAt`) is refused (`ScheduledBeforeFreeze`), so every unfreeze waits a full `adminDelay` after the latest freeze. Known limit: the freezer's veto has no exception, so a stolen freezer key can keep the vault frozen by cancelling every unfreeze and every change of the freezer (`test_KnownLimit_FreezerCanVetoItsOwnReplacement`; no funds move, the remedy is a new vault).
    - **Always timelocked (no direct setter):** lifting freezes (`Unfreeze`, `UnfreezeAll`), changing the freezer (`SetFreezer`), proposing a new admin (`ProposeAdmin`, still followed by `acceptAdmin`), changing the fee recipient (`SetFeeRecipient`).
    - **Instant when tightening, timelocked when weakening:** `setCaps` / `setGlobalCaps` (enabling caps from disabled, lowering caps, or lengthening the window stay instant; raising caps, shortening the window, or disabling caps with `window = 0` revert `TimelockRequired`), `setCapWeight` (raising weight stays instant; lowering reverts `TimelockRequired`), `setReleaseDelay` (raising stays instant as an emergency brake; lowering reverts `TimelockRequired`), and `setFees` (lowering stays instant; raising any deposit or withdraw fee reverts `TimelockRequired`).
    - **Always instant:** `freeze` / `freezeAll` (safety moves fast), `deregisterToken`, `registerToken`, `addDenomination`, and `setRelayFeeMenu` (relay fees are optional user-chosen tips bound into each G3 proof, fee 0 is always allowed, and every entry is capped at 2%). Verification parameters (`verifier`, image IDs, LEZ IDs, `cfgId`, `minReleaseDelay`, `adminDelay`) remain immutable with no setter at all (S#8).
  - Release delay (F#12): an exit root recorded at time t waits, per token, the lowest delay in force at any moment since t: the delay when it was recorded, cut by any later lowering. A raise applies only to roots recorded after it, never lengthens a recorded root's wait, and never makes a releasable root wait again; a root in the same second as a change gets the lower of the two. `releasableAt(token, root)` gives the time; `releaseDelayState(token)` and `delaySteps(token, i)` expose the per-token history.
  - Relay-fee menu: `setRelayFeeMenu(token, uint256[][])` (admin only) sets at most 4 non-zero relay fees per denomination, each within the 2% bound; fee 0 (self-submission) is always allowed. A non-zero fee needs a relayer (`ZeroRelayer`) and a value on the menu (`RelayFeeNotOnMenu`). The exit commits only to `maxRelayFee`, so a menu change never strands an exit (`test_MenuChangeNeverStrandsExit`).
  - Payees: `release` refuses recipient = the vault or address(0) (`BadRecipient`) and a fee-earning relayer = the vault (`BadRelayer`). The recipient is fixed in the exit commitment, so an exit burned to such an address can never be released; clients must refuse to build one.
- **Fixed verification:** the verifier address and the image IDs are immutable, so verification can't be swapped.
- **Deposit desk (demo networks only; deployed on Sepolia in front of v2, `DEPLOYMENTS.md`):** `src/desk/DepositDesk.sol` sits in front of a vault and takes a bridge fee of `feeBps` (owner-set, hard cap 300 = 3%, rounded down; **30 = 0.3% on Sepolia since 2026-11-14**, `script/SepoliaDeskSetFee.s.sol`) of the denomination, in the deposited asset, on top of the vault's amount; it forwards the deposit in the same call, so the leaf is the same as a direct deposit's, and emits `FeePaid(token, lezPublicKey, commitment, denomIndex, leafIndex, fee)`. ETH: `msg.value` must equal the total. ERC-20 (since 2026-11-27): `depositWithFee(token, denomIndex, commitment, lezPublicKey, maxTotal)` reverts `WrongAmount` when the quoted total exceeds `maxTotal`, even with a larger standing allowance; it replaces the four-argument call, which the deployed desks (v2 to v5) keep, so this applies to a new desk only. The owner can set the rate within 3% and withdraw collected fees, nothing else. Not part of the trust-minimised bridge (`DESIGN.md` §3.6). Runtime 3,941 bytes with `maxTotal` (`forge build --sizes`, Foundry v1.5.1, Colab CPU runtime 2026-11-27; 3,932 before, CI run `43501320143`). Tests: `test/DepositDesk.t.sol` (29, against the real vault), `test/SepoliaDeskScript.t.sol` (2). Deploy: `script/SepoliaDesk.s.sol`; change the rate: `script/SepoliaDeskSetFee.s.sol` (owner key, `FEE_BPS`; `DEPLOYMENTS.md`). The production fee is the vault's own `depositFee`/`withdrawFee` (≤ 2%); fee policy and what the fee funds: `../research/open-settlement.md`.

**Gas** (`../research/gas-sepolia-vs-local.md`): transaction receipts from a local anvil (Foundry 1.9.0), mock verifier, caps on, measured on the v1 source.
