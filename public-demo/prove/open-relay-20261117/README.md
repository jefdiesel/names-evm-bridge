# Open claim relay and sponsored private burn (branch `open-relay`, 2026-11-17)

State labels as in `DESIGN.md`: (1) run on a chain (which one is named), (2) tested in simulation or unit tests only, (3) designed only. Nothing here is deployed; the public demo chain, its relayer and Sepolia were not touched. The bridge program changes on this branch, so its image id changes (`node scripts/check-versions.mjs`: 0 FAIL, 15 WARN (all pre-existing accepted entries), 1 SKIP, 139 OK; the CLI and guests built on this branch are not installed anywhere; no deployed image is pinned to this build).

## What was built

**A. Open claim relay.** `Instruction::Relayed { refund_to, claim }` wraps a public claim (`Claim` or `ClaimAttested`, no one-time recipient). After the claim's own three messages, the claimer's actor sends `Effect::Refund { to }` and the config pays exactly `Config::relay_refund` of native LEZ from its float to `refund_to`, in the same transaction (`lez-bridge/bridge/src/lib.rs`, "Open claim relay").

- Paid only when the claim applies: the refund is a later message of the same transaction, so a refused claim reverts it.
- At most once per deposit (the claim nullifier), and never more than the configured amount: the instruction carries no amount, the admin sets it (`set-relay-refund`), the program caps it at `MAX_RELAY_REFUND` = 2,500,000.
- No allowlist anywhere: any account may be the payee. LEZ gives a program no view of the fee declaration (`ReceiveInput` has `receiver`, `from`, `is_authorized`, `pre_state`, `message` and nothing else, `lee/state_machine/core/src/program/mod.rs` 373-385 at v0.4.0-rc3), so the program refunds the account the claimer's signed instruction names. The claimer's signature covers the whole message (payee, fee payer, nonces), so nobody can change the payee after signing. A relay co-signs only a claim naming its own payer (`relay-cosign` refuses another payee; it allows exactly one declared actor of its payer, its native balance, which the refund credits; `--require-refund` refuses unrefunded claims and checks that the float covers the refund now).
- A float holding less than the refund fails the refunded claim whole (nothing minted, nullifier unspent). A claim that names no payee never touches the float. This deviates from `research/open-settlement.md` §3, which proposed `min(refund, float)`: reading the float needs a `ReadState` round trip the program does not make.
- A one-time recipient (a private claim) is refused under `Relayed`: it already draws the sponsor amount, so one deposit draws the float once.
- Client: `claim --relay A,B` (tried in order) or `--relay config` (the list in `LEZ_BRIDGE_RELAYS`), and a single `--relay URL` per claim (RFP-022 Privacy Preservation #6). The client moves to the next relay when one is unreachable or refuses before submitting. It should be safe even when the first relay did submit after all: every attempt carries the claimer's same nonce, so by LEZ's nonce rule at most one can apply and a later one is refused without charge (`DESIGN.md` §3.6). That follows from the rule; the run shows only the unreachable case (A3), not a relay that submitted and then failed to answer.
- Relay daemon: `public-demo/relayer/relayer.py` already takes its payer, wallet, port, state and log from its environment; a second instance runs beside the first with its own key and no registration. New: `REQUIRE_REFUND=1` (passes `--require-refund`; `refund_required` in `/relay/info`).

**B. Sponsored private burn.** A burn may name as `notify` not the config but the bridge's actor of a fresh one-time private account `W` of the burner's wallet. That actor forwards the token program's notice to the config (`Effect::SponsoredBurn { token_program, notice, to: W }`); the config records the burn exactly as a direct notice (freeze, denomination, `burned <= claimed`, `Exited`) and pays `Config::burn_sponsor` (admin-set, `set-burn-sponsor`, capped at `MAX_BURN_SPONSOR` = 6,500,000, about one burn's fee) to `W` in the same transaction, from the **burn float**, a PDA of its own (opened by `set-burn-sponsor`, funded with `fund-float --burns`), so claims and burns cannot drain each other's float. At most one sponsored burn per claim (`Config::sponsored_burns` against the claims of every token). The stock rc3 wallet promotes the credit to `W` because its witness names `W`, and `W` pays the fee (`lez-bridge burn --sponsored`; the CLI makes `W` and names it the fee payer). The config pays only a forwarder presented under an alias: LEZ presents a private sender to a public receiver under a blinded alias and a public sender under its own id (`lee/state_machine/core/src/execution_state.rs` `sender`, 1409-1430), so `from == to` means a public forwarder, refused (`SPONSORED_BURN_PRIVATE`). Only a public `W` is refused: a public burner naming a private `W` is paid, and pays the private transaction's fee from it. Without that check a public burner could name its own bridge actor, pay only a public fee (a refunded public claim cost about 1.49M here; a public burn's fee was not measured, only its reverted cost at 2,000,000 declared gas, 16,005,880) and collect the 25M sponsor. G2-lite counts a sponsored burn from the private forwarder's boundary effect only, never from the root call (`lez-bridge/outbound/core/src/view.rs`).

Why not something smaller:
- LEZ 0.4 has no third-party payer for a private transaction's fee: the fee is the one native `Credit` crossing into the fee inbox from a private account of the transaction (`lez/chain_state/src/classify.rs` `private_fee_reserve`, 65-93), so the value must reach a private account of the burn inside the proof.
- Paying the notice's sender instead (no new account): the sender is a presentation alias with a random factor (`lez/wallet/src/account_manager.rs` `presenter`, 732-748), which the executor does resolve (`lee/state_machine/core/src/execution_state.rs` `sender`, 1409-1430, `register_alias`), but the stock wallet promotes an async credit only to an account its witness names (`lez/wallet/src/lib.rs` 1703-1704: `!listed_only && witnessed.contains(&body.to.account_id)`), so the credit would not arrive inside the proof. That needs a wallet change, not a bridge change.
- Paying an alias `V.blinded(o)` of the burner, as the claim does: the burner's token actor would have to carry `o` to the config, which needs a new token-program message (the notice is fixed at definition, amount and memo, and the memo is the exit commitment `E`). The one-time account needs no token change.
- Deducting the fee from the burn: a burn is exactly one denomination (`DESIGN.md` §3.5), and minted value is public.

## The refund and its bound

- **Per claim:** exactly `relay_refund`, fixed by the admin, at most `MAX_RELAY_REFUND` = 2,500,000 by the program; the instruction carries no amount.
- **Per deposit:** at most one refund (the claim nullifier), and none for a claim that fails (A4; native `a_failed_claim_refunds_nothing`). A one-time (private) claim takes the sponsor amount instead, never both.
- **A griefer draining the float with real claims of its own cheap deposits:** every refund needs a real vault deposit (the smallest denomination locked, plus Ethereum gas), and the drainer pays the claim's own fee. At the run's values (refund 1,300,000, fee charged about 1,486,208) each refunded claim costs its payer about 186,208 net, so draining is a loss in native LEZ as well as in Ethereum gas; draining a float of F takes F ÷ 1,300,000 deposits (about 770 for the run's 1,000,000,000). The locked deposits are not lost (they can be burned and released), so the real cost is gas on both chains. If the admin set the refund above the fee a claim actually pays (up to the cap), a self-paying claimer would keep the difference once per deposit: at most 2,500,000 − 1,486,200 = 1,013,800 per deposit at this run's fee. The admin should keep the refund at or below the measured fee.
- **An empty or short float:** a refunded claim fails whole (nothing minted, nullifier unspent); `relay-cosign` refuses to co-sign when the float holds less than the refund, but a float drained between the check and inclusion would fail the claim and cost the relay its declared fee, as A4 did for a freeze. A claim naming no payee never touches the float.
- **The sponsored burn (fixed after review, 2026-11-17):** exactly `burn_sponsor` per burn, at most `MAX_BURN_SPONSOR` = 6,500,000, about one burn's fee (5,425,752 charged in dev mode in run 4 and 5,433,648 in run 5; a proved burn's fee is not measured; the CLI prices the in-proof reserve one block of fee climb ahead, about 6.1M, instead of the wallet's default five blocks, so the sponsor covers it). At most one sponsored burn per claim: before the fix one 1000 deposit burned as ten 100s drew ten 25,000,000 sponsors, about 40 such burns emptied the run's float; now the second sponsored burn of that claim is refused (`one_large_claim_split_into_small_burns_draws_one_sponsor`) and the rest burn directly. Per real deposit (claimed, then burned) the most a burner keeps is the sponsor minus the burn's fee: 1,066,352 at the cap in run 5, against the Ethereum gas of a deposit and a release. The sponsor comes from the burn float, its own account: draining it stops sponsored burns only, and draining the claims' float never stops them (`the_claims_float_and_the_burn_float_cannot_drain_each_other`). Only a private forwarder is paid (a public `W` is refused, run step B0).
- **Fingerprint:** one refund value and one burn-sponsor value for every claim and burn in a given configuration (`every_refund_is_the_same_amount_and_the_same_messages`). A refunded claim is still distinguishable from an unrefunded one (it carries `Relayed` and two more actors), and a sponsored burn from a direct one (a `SponsoredBurn` effect and a credit to a fresh account).

## What a relay learns

A relay receives the half-signed public claim before it lands: the claimer's account, the deposit secret `k` (a public claim publishes it anyway once it lands), the leaf index, the root and the claimer's network address. It cannot:
- redirect the mint: the commitment binds the claimer, so a claim of the same deposit signed by the relay is refused (`a_relay_that_learns_the_secret_cannot_redirect_the_mint_or_burn_the_deposit`);
- burn the deposit with a cheaper one of its own made with the same `k`: the nullifier binds the destination, token and denomination (review H2, fixed 2026-11-14); its own deposit spends its own nullifier and the claimer's claim still applies (same test);
- change the payee or the fee: the claimer's signature covers the whole message (`a_refunded_claim_must_name_this_relay_s_payer_and_nothing_else_of_it`);
- censor selectively for good: the claimer picks another relay per claim, or lists several (run step A3).
It can refuse service, and it sees which account claims which deposit, as any public claim publishes. The refund is one fixed value for every refunded claim (`every_refund_is_the_same_amount_and_the_same_messages`), so it is no fingerprint; the relay's payer is public as the fee payer in any case.

## What is not shown

- **A burner holding exactly zero native LEZ:** not run. V held 19,370,496 (left from its own sponsored claim) during the burn; the run shows that V's balance did not move and that the one-time account started empty and paid the fee. The program never reads the burner's balance, but a zero-balance burner was not shown.
- **The core module cannot read a config of this branch:** `modules/lez_bridge/rust-lib/src/lez.rs` decodes the bridge `Config` field by field and refuses trailing bytes ("it may be a newer bridge"), so the two new fields (`relay_refund`, `burn_sponsor`) make it fail closed on a deployment of this bridge. Not changed here.
- **The relay takes stand-in claims only:** `relay-cosign` still refuses a config whose roots come from RFP-021 (`ClaimAttested`); the program refunds a relayed `ClaimAttested` (native test), the relay does not co-sign one yet.
- **No proof:** the private claim and burn ran with dev receipts (LEZ dev mode). A proved sponsored burn has not run; whether the stock wallet proves it in the same shape is expected (the dev-mode run used the same code path to the prover) but not shown. The private transactions' fees above are dev-mode fees.
- **No G2 update or release:** the run stops at the burn. G2-lite's extraction of the new shapes is covered by the outbound tests above (one updated case), not by an update over these blocks.
- **The relay list is CLI-only:** the core module and the Names Wallet still send a plain claim (`modules/lez_bridge/rust-lib/src/relayed.rs`, golden vector unchanged); a relay with `REQUIRE_REFUND=1` refuses those, one without it relays them unrefunded. The client list takes loopback relays and the chain's own endpoint only (`allowed_relay`); a non-loopback relay URL is not supported yet.
- **Non-loopback relays, discovery and the RPC filter:** each relay here was reached directly on loopback; the demo chain's filter (`bridge_relayClaim`) still names one relay. No relay discovery exists.
- **Not deployed:** the public demo chain, its relayer, the module and the deposit page are unchanged. Deploying this needs a new bridge instance (new image), hence a new vault.
- **The sponsored burn's one-time account keeps its leftover** (the sponsor minus the fee, 1,066,352 here) in a private account of the burner's wallet; nothing sweeps it yet.
- **What a relay sees of a burn:** not applicable; the sponsored burn needs no relay.

## Known limits and next steps

Not fixed on this branch (a demo-level bar, by the owner's steer); each is a next step:

- **An empty float blocks claimers with no LEZ.** A refunded claim fails whole when the claims' float holds less than the refund, and a sponsored one-time claim when it holds less than the sponsor; the CLI does not fall back to a plain (unrefunded) relayed claim.
- **Relays do not account for refunds not yet landed.** `relay-cosign` checks the float against one refund, not against the refunds of its own co-signed claims still in flight; a float drained in between makes the claim revert and costs the relay its declared fee (1,853,280 here, run step A4).
- **Config decoding is not versioned.** This branch's CLI and relayer decode the bridge `Config` with the two new trailing fields and `sponsored_burns`, so they cannot read the v2–v5 configs; the core module's decoder (`modules/lez_bridge/rust-lib/src/lez.rs`) refuses the new ones (fail closed). A versioned decode is needed before any deployment.
- **The refund cap exceeds a refunded claim's fee.** `MAX_RELAY_REFUND` = 2,500,000 against about 1,486,208 charged here, so with the refund set at the cap a self-paying claimer keeps about 1,013,800 per real deposit. The run set 1,300,000; lowering the cap is a one-line change.
- **Freshness of `W` is enforced only by the CLI.** The program pays any private forwarder; reusing a one-time account links the burns that reuse it (privacy, not funds).
- **Failover shows the claim to every relay tried,** and a relay that answered "refused" can still submit the half-signed transaction it received (the claimer's nonce lets at most one land).
- **Untested:** a sponsored burn that reverts after inclusion (its cost to the one-time account), and proved (not dev-mode) private claims and burns.
- **Every native test sets `atomic_asyncs = true`:** the simulator then undoes a whole transaction on a failed async credit, as LEZ does for a public payee or a promoted private credit; an unpromoted credit's behaviour is not modelled.
